### 3.4 本仓已有等价实现（不重复移植）

- 「抢任务栏」同一 tick 去重：`taskbar.rs` 的 `Tug::shown` 早于上游，写法等价（2.0.3 已判定）。
- 宠物图库走网络代理：本仓 `fetch.rs` 比上游更严格（2.0.3 已判定）。
- 卡死抓栈：本仓已有 `crash::Hang` + `stack_of`；上游本次只是改抓栈时机与守护进程行为，主体不重复。

## 四、为什么不整体合并

- **体量**：185 个提交，0.4.3 一个版本就 140 个；`compare` 的文件数组在上限 300 处被截断，实际改动面更大。
- **依赖**：顶栏 + dock、嵌入任务栏、HTML 邮件、媒体会话都建立在因子上游 0.4.x 新增的窗口 / 页面 / 插件子系统上；本仓没有这些子系统。
- **产品语义**：本仓 2.2.x 的「家」、插件协议、安装资源、数据根与上游不同；整体合并会同时改动用户数据兼容、插件 API 与发行口径，超出一次更新的验收能力。
- **教训**：2.0.3 的先例是「逐项判定、能合则合、不能合就写明原因」；0.4.x 沿用同一方法，但这次可合的只有安全修复一项。

## 六、方法与证据边界

- 用 GitHub API 的 `compare` 取提交与文件清单；`files` 最多 300 条，**不能用它的 additions/deletions 当全量改动量**。
- 四份 release note 只作为「上游自己怎么说」的线索；判定以 patch 与本仓代码为准。
- 版本归属不靠 release note 猜：`e143563e` 的父提交是 `387a1ec1…`（v0.4.2 的 tag 提交），它本身是 v0.4.2 之后的第一个提交，首次随 v0.4.3 发布。复现包把它记成 v0.4.2，本仓不沿用这个错误。
- 候选提交只读了 patch 的文件清单与关键片段；没有在本仓逐行移植验证，所以标「候选」而不是「可合入」。
- 上游 `main` 在 v0.4.3 之后可能还有新提交；本文件只对 2026-11-15 之前的 v0.4.3 负责，下一次跟进重新取区间。
