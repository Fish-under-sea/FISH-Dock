# Dock 2.2.2 设计：外部窗口 Hook 补齐 12 项缺口

> 状态：**已实施 11 项，4 项顺延**（详见文末「实施结果」）。
> 基线：2.2.1（`8891c9e`）。来源：[issue #87](https://github.com/Fish-under-sea/FISH-Dock/issues/87)、待办 `archive/issue-drafts/todo-87-host-side.md`。

## 〇、一句话范围

补齐外部原生窗口 Hook 的 12 项能力，让「悬浮小球 + 暂存长条」这类形态可以完整复刻。**全部改动只作用于插件自己的窗口，主岛（`island.rs`）的绘制、布局、动画一行不改。**

## 一、总原则

### 1.1 影响面边界

| 模块 | 本次是否改动 | 说明 |
| --- | --- | --- |
| `island.rs` | **仅新增只读取数** | 暴露胶囊矩形与视图状态给 `plugin_window`，不改现有渲染逻辑 |
| `plugin_window.rs` | 主要改动 | 窗口选项、命中测试、几何、事件 |
| `dropwin.rs` | 小幅 | 支持 drag-out 的源窗口判定 |
| 前端 `app/src/pet/` | 仅新增上报 | 把已有的 `view`、胶囊尺寸多报一份，不改布局 |
| SDK 两侧 | 新增方法 | `plugin.mjs`、`bridge.js` |

### 1.2 兼容性

- 新增字段全部**可选**，缺省行为与 2.2.1 完全一致。
- 已有 `anchor` 三值、`width`/`height` 数值范围、事件载荷字段**不改语义**，只增不删。
- 旧插件（含当前 filemgr 1.0.13）行为不变。

### 1.3 零影响保证：按需启用（关键约束）

**问题**：主岛页面常驻运行（`island.rs:662` 建窗，`WebviewUrl::App("pet/index.html?role=island")`），不装任何插件也在跑。而 C1 需要的 `view` 上报必须加在页面里，`update()` 有 37 处调用点（`island.js`）。若直接写入，**所有用户**每次更新都会多一次 IPC——这是不可接受的外观/性能回归。

**约束**：新增的页面→宿主上报**必须**由宿主按「有没有插件在听」显式开关，默认全关。

**机制**

1. 宿主维护 `dock_watchers: usize`，等于订阅了 `dock.onEvent` 的插件数。
2. `0 → 1`：宿主向主岛页面发 `island:watch-dock`（带 `on: true`），页面开始上报。
3. `1 → 0`：发 `on: false`，页面停止上报并清空缓存。
4. 页面侧上报函数第一行 `if (!watching) return`，未开时零成本。

**由此得到的保证**：

| 场景 | 新增代码是否执行 | 外观 | 性能 |
| --- | --- | --- | --- |
| 不安装任何插件 | 否 | 不变 | 不变（`dock_watchers` 恒 0） |
| 安装但未启用 | 否 | 不变 | 不变（后端不启动，无法订阅） |
| 启用但没订阅 `dock.onEvent` | 否 | 不变 | 不变 |
| 启用且订阅了 | 是 | 仅插件窗口变化 | 有上报，但只在订阅期间 |

**同理适用于**：C5 的指针事件、E4 的动画帧上报、B4 的命中矩形上报。全部挂在同一个 `watching` 开关下。


## 二、逐项设计

### C1 主岛几何读取（前置）

**接口**

```
FishDock.dock.rect()  →  Promise<DockRect | null>
context.dock.rect()   →  Promise<DockRect | null>
```

```ts
type DockRect = {
  window:  { x, y, width, height },   // 主岛窗口矩形（物理像素）
  capsule: { x, y, width, height } | null,  // 可见胶囊矩形；尺寸未知时为 null
  state: {
    view: 'compact' | 'expanded' | 'settings' | 'ask',
    stowed: boolean,        // 已滑出屏幕
    hidden: boolean,        // Dock 全局隐藏
    fullscreen: boolean,    // 有窗口全屏，主岛避让
  },
  scale: number,          // 该屏 DPI
}
```

**为什么必须两个矩形**：主岛窗口铺满工作区宽（1920），胶囊只有 240/300/380。只给一个都不够用。

**数据来源**

| 字段 | 来源 | 现状 |
| --- | --- | --- |
| `window` | `geometry_of(island)` | 已有（`plugin_window.rs:622`） |
| `capsule` | `island::closed_rect()` | 已有（需暴露为 `pub`） |
| `view` | **需新增上报** | 页面有 `island.dataset.view`（`island.js:4901`），宿主不知道 |
| `stowed` | `isl.stow.stowed` | 已有（`set_stow` 已收） |
| `hidden` | `book.dock_hidden` | 已有 |
| `fullscreen` | `isl.over_full` | 已有 |

**唯一新增的数据流**：页面 → 宿主的 `view` 上报。复用现有 `window.pet.stow(on, width, height)` 的模式，新增 `window.pet.view(name)`。

**上报点**：`island.js:4901` 设 `island.dataset.view` 之后，加一行 `if (dockWatching && view !== lastReportedView) { lastReportedView = view; window.pet.view(view) }`。

**为什么加 `view !== lastReportedView` 去重**：`update()` 有 37 处调用点，但 `view` 实际变化很少（compact/expanded/settings/ask 四态切换）。去重后实际 IPC 次数等于视图切换次数，可忽略。

**必须受 §1.3 的 `watching` 开关约束**：未开时一行都不执行。


### C2 主岛几何/状态事件

**接口**

```
FishDock.dock.onEvent(listener)  →  () => void
context.dock.onEvent(listener)   →  () => void
```

**事件载荷**

```ts
{ event: 'dock', type: 'geometry', rect: DockRect }   // 几何或状态变化
```

**触发条件**（去重，只在不一致时发）：
- 主岛窗口矩形变化（已有 `dock_changed`）
- 胶囊矩形变化（新增，见 C3）
- `view` / `stowed` / `hidden` / `fullscreen` 任一变化

**节流**：最小间隔 16 ms（约 60 fps 上限），避免滑动动画期间刷爆队列。滑动期间仍需逐帧推（E4 要求），所以不用更长间隔。

**推送方式**：`plugin.windowEvent` 通道，`event: 'dock'`。SDK 按 `event` 分流到 `dock` 监听器集合。

### C3 锚定窗口随胶囊重排

**问题**：现在重排挂在主岛窗口的 `Moved`/`Resized`/DPI 上，但主岛窗口宽恒为工作区宽、高固定 132，胶囊形态变化不改这个矩形，所以永不触发。

**改法**

1. `island.rs` 在 `set_stow`、`set_room`、以及页面上报 `view` 后，调用新增的 `plugin_window::capsule_changed()`。
2. `capsule_changed()` 重新计算 `closed_rect()`，与上次缓存比较，变了才 `rearrange()`。
3. `rearrange()` 不变——它本来就只遍历 `book().windows`（插件窗口）。

**新增缓存**：`static CAPSULE_RECT: Mutex<Option<(i32,i32,i32,i32)>>`，与现有 `DOCK_RECT` 并列。

**作用对象**：`rearrange()` 里只对 `app.get_webview_window(&rec.label)` 调 `place()`，主岛窗口不在集合里。

### C4 宽度绑定主岛（绑胶囊 + maxWidth）

**接口变更**

```
width: number | 'dock'      // 'dock' = 跟随胶囊当前宽度
maxWidth?: number            // 仅 width:'dock' 时有效；内容可增长到的上限（逻辑像素）
```

**语义**

- `width:'dock'`：窗口宽度 = 胶囊当前宽度（逻辑像素），随胶囊变化实时更新。
- `maxWidth`：缺省 = 胶囊宽度（即恒定等宽）；给定则允许插件用 `windows.update` 把宽度增到 `maxWidth` 以内，宿主不再覆盖。
- `maxWidth` 上限受 `WIDTH_MAX`（2400）约束；小于胶囊宽度时按胶囊宽度算。

**实现**

- `Options.width` 从 `f64` 改为 `enum Width { Fixed(f64), Dock }`。
- `Rec` 增加 `max_width: Option<f64>`。
- `place()` 里 `Dock` 分支取 `closed_rect()` 的宽度；拿不到时回落到 `WIDTH_DEFAULT`。
- `capsule_changed()` 触发时重算。

**为什么不是绑工作区宽**：通栏 1920 明显不是插件要的，且改回来是破坏性变更。

### C5 主岛交互事件

**接口**：并入 C2 的 `dock.onEvent`，新增事件类型：

```ts
{ event:'dock', type:'pointer', action:'enter' | 'leave' | 'down' }
```

**数据来源**：主岛页面已有 `window.pet.hover`、`window.pet.onPress` 等回调。新增 `window.pet.dockPointer(action)` 上报。

**用途**：插件据此把长条收成小球。

**注意**：这是**主岛**的指针事件，与拖入的 `enter`/`leave`（`fileDrop`）是两回事，命名上要区分开。

### B1 更小窗口 + fitContent

**接口变更**

```
width/height 下限：160×80 → 32×32
fitContent?: boolean         // true 时窗口尺寸由页面内容决定
```

**fitContent 实现**：页面在 `window.js` 容器里用 `ResizeObserver` 观察 `body`，通过新增的 `plugin_window_resize` 命令上报尺寸，宿主 `set_size`。上限仍受 `WIDTH_MAX`/`HEIGHT_MAX` 约束。

**风险**：缩小下限后，`transparent` 窗口的透明区问题更明显（见 B4）。所以 B1 与 B4 需一起做，否则小窗口反而更难用。

### B2 锚点对齐语义

**接口变更**

```
align?: 'right-top' | 'right-center' | 'right-bottom'
      | 'left-top'  | 'left-center'  | 'left-bottom'
      | 'top-center' | 'bottom-center'
```

**语义**：指定**窗口的哪条边/角**贴住锚点。

| anchor | align 缺省 | align 生效后 |
| --- | --- | --- |
| `dock-left` | `right-center`（现状：窗口右缘贴主岛窗口左缘、垂直居中） | 按 align 指定的边/角贴合胶囊的对应边/角 |
| `dock-bottom` | `top-left` | 按 align 贴合胶囊 |

**关键改动**：`dock-left`/`dock-bottom` 的基准从**主岛窗口矩形**改为**胶囊矩形**。这是行为变更，但符合直觉且是插件方明确需要的。

**兼容性**：为保证旧插件行为不变，新增 `anchorBase?: 'window' | 'capsule'`，缺省 `'window'`（旧行为）。只有显式写 `anchorBase:'capsule'` 才走新基准。

### B3 drag-out

**接口**

```
context.windows.beginDragOut(handle, paths)  →  Promise<{started:boolean}>
FishDock.windows.beginDragOut(handle, paths)
```

**实现**：宿主侧用 `DoDragDrop` + 自建 `IDataObject`（`CF_HDROP` 格式），把路径交给资源管理器。需要在主线程调用，且拖拽期间不阻塞。

**可行性**：`dropwin.rs` 已有 `DragQueryFileW` 等 Win32 绑定，但**没有** `DoDragDrop` 的源侧实现。这是本次**工作量最大、风险最高**的一项——OLE 拖拽源涉及 COM 接口实现，且必须在 STA 线程。

**建议**：先做探路（spike）验证 `DoDragDrop` 在 Tauri 主线程可用，再决定是否本版交付。

### B4 透明区点击穿透

**接口变更**

```
hitTest?: 'window' | 'opaque'    // 缺省 'window'（现状）
hitRects?: Array<[x,y,w,h]>      // 可选，显式指定可点击区域（页面逻辑像素）
```

**实现**

- `hitTest:'opaque'`：页面用 `ResizeObserver` + `getBoundingClientRect` 上报不透明元素的矩形（复用 `island.rs` 的 `solid` 机制思路）。
- `hitRects`：直接给定矩形。
- 宿主用 `set_ignore_cursor_events` + 轮询光标位置切换（复用 `pointer.rs` 的 `ClickThrough`，它有成熟的三态与防抖）。
- 光标在命中区内 → `Catch`；在外 → `Pass`。

**与 B1 的关系**：B1 让窗口变小，B4 让透明区穿透。两者一起做效果最好。

### D2 打开内部插件页

**接口**

```
FishDock.plugin.openPage(pageId)  →  Promise<{opened:boolean}>
context.dock.openPage(pageId)
```

**实现**

- 校验 `pageId` 是本插件已登记的 `pages[].id`。
- 宿主侧调用设置面板的既有开页入口（`settings.js` 的 `open(key)` 路径）。
- 能力要求：`windows`（已有）或新增 `pages` 能力？**建议复用 `windows`**，不新增能力，减少插件改清单。

### E1 落点坐标

**载荷变更**

```ts
{ event:'fileDrop', scope, handle, phase:'drop', paths,
  position: { x, y, clientX, clientY } }   // 屏幕物理坐标 + 窗口内逻辑坐标
```

**实现**：`dropwin.rs` 的 `WM_DROPFILES` 处理时已有光标位置（`GetCursorPos`），补进载荷。`clientX/clientY` 由宿主按窗口 rect 换算。

### E2 失焦/点外部事件

**接口**：并入 `windows.onEvent`，新增：

```ts
{ event:'blur', handle }
{ event:'focus', handle }
```

**实现**：`window_event` 里加 `WindowEvent::Focused(bool)` 分支，向上发事件。

**限制**：这是**本窗口**的焦点变化，不是「点窗口外部」。真正的「点外部」需要全局钩子，本次不做——文档写明用 `blur` 近似。

### E3 完整状态枚举

并入 C1 的 `state.view`：`compact` / `expanded` / `settings` / `ask`，加 `stowed` / `hidden` / `fullscreen` 三个布尔。

**数据来源**：页面 `island.js:4863` 的 `view` 计算已经涵盖前四个值，只需上报。

### E4 动画期间胶囊矩形

C2 的 `geometry` 事件在滑动动画期间逐帧推送。

**问题**：胶囊滑出是页面内 CSS `transform`（`style.css:2991`），宿主不感知。要在动画期间逐帧推，需要页面在动画期间持续上报胶囊位置（`requestAnimationFrame` 内）。

**代价**：这是本次**唯一需要页面高频上报**的项。建议只在 `stowed` 状态切换后的 300 ms 内启用 rAF 上报，之后停止。

### E6 z-order 与 room 申报

**接口**

```
zOrder?: 'normal' | 'above-dock'   // 缺省 'normal'
```

**实现**：`above-dock` 时对插件窗口设 `always_on_top`。主岛窗口本身是 `always_on_top(true)`，所以「above-dock」意味着也在置顶层，需要 `SetWindowPos` 排到主岛之前。

**room 申报**：**本次不做**。旧产物的 `roomOver` 是同一进程内的布局协商，跨窗口语义不清晰，且与 C4 的 maxWidth 功能重叠。文档标注为「不支持，用 maxWidth 替代」。

### E7 跨窗口动画

**本次不做**，文档化：跨窗口动画不支持，建议改为窗口内动画。理由：全屏动画层是独立子系统，与本次范围无关。

## 三、实施顺序

依赖关系决定顺序，不能并行：

```
1. C1（含页面 view 上报）        ← 一切几何的基础
2. C3 + C4（依赖 C1 的胶囊矩形）
3. C2 + C5 + E3（依赖 C1 的状态）← 事件系统一次做完
4. E4（依赖 C2）
5. B1 + B4（互相配合）
6. B2（锚点重构，依赖 C1）
7. E1 + E2（载荷与事件，独立）
8. D2（独立）
9. B3（探路后决定）
```

## 六、风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **B3 OLE 拖拽源** | 工作量最大，COM 接口实现复杂，可能本版做不完 | 先探路，失败则推迟到 2.2.3 |
| **E4 高频上报** | 动画期间 rAF 上报可能影响主岛性能 | 限制在 300 ms 窗口内，之后停 |
| **B2 基准变更** | 从窗口矩形改胶囊矩形是行为变更 | 用 `anchorBase` 显式切换，缺省保持旧行为 |
| **B1+B4 同时做** | 两个机制交互复杂（窗口变小 + 命中测试） | 先做 B4（保留大窗口），再做 B1 |
