# FISH Dock 2.2.0：插件外部原生窗口 Hook 与 Setup 单包更新规格

状态：维护者已于 2026-11-08 批准实施，正在实现与验证。依据：PR #77、issue #76，以及维护者确认的 2.2.0 发版策略。逐项进度与新增 WebView2 预检误报修复见 [执行计划](2026-11-08-dock-2.2.0-plan.md)。

## 1. 目标与范围

Dock 提供通用 Hook，第三方插件显式调用后，由 Dock 创建位于主 Dock 外部的第二个独立原生窗口，插件在该窗口内绘制自己的业务界面。插件提供页面资源、业务交互及显示时机；Dock 承担原生窗口承载、受控通信、拖入路由和生命周期回收。没有插件请求创建时，Dock 不创建、不绘制第二个窗口，也不预建隐藏 WebView。外部原生窗口与 Dock 设置面板内部的插件显示区是两种独立承载模式。

Hook 的正式接入说明必须同时写入官方插件仓库 `Fish-under-sea/FISH-DOCK-Plugins` 的开发者文档，并从该仓 `docs/developers/README.md` 直达；不能只保存在 Dock 宿主仓。

2.2.0 是最后一个同时发布 Setup 和 Update 的过渡版本。2.2.0 宿主自身检查和安装更新时只认 Setup；后续发行只提供 Setup 与对应摘要。安装事务、失败回滚、用户资料保留继续有效。

本轮不升级官方插件，不代第三方文件管理插件实现暂存条，不修改用户现装程序，不增加其他插件市场或通用任意程序启动能力。

## 2. 已确认的存量问题

- `app/src/pet/island.js` 的 `stashSub` 在主岛初始化时直接创建 UI，并固定调用 `jassdingk.filemgr`。
- `visible()` 在正常状态始终返回 true，`refresh()` 对未安装或未运行插件的错误静默后仍绘制。关闭按钮实际上只是收起为小球。
- 子岛 UI 实际属于主岛 DOM，通过实体命中区与扩窗逻辑获得显示空间，并非第二个原生窗口。
- `dropwin.rs` 固定把文件路径发往 island，宿主页面再调用文件管理插件。现有路径没有插件订阅者身份或代次隔离。
- 插件页面资源协议目前只允许 island 承载。浏览器 SDK 依赖父页面消息桥；插件后端的宿主回调目前仅接存储能力，不能直接复用成窗口 API。
- 更新存在两层回退：`updates.rs` 优先下载 Update、失败再尝试 Setup；增量包生成器又嵌入 `update-fallback.ps1`，安装事务失败后下载并运行 Setup。

## 3. 方案取舍

| 方案 | 结果与成本 | 决定 |
| --- | --- | --- |
| 给宿主暂存 UI 加关闭开关 | 能隐藏小球，仍绑定具体插件与主岛 DOM | 不采用 |
| Dock 承载独立原生 WebView 窗口，加载插件资源 | 复用现有页面票据和 SDK；插件掌握 UI，Dock 可统一回收窗口 | 采用 |
| 插件自带任意原生程序并把 HWND 交给 Dock | 跨进程所有权、焦点、回收与安全边界复杂，不能复用页面 SDK | 不纳入本轮 |

本规格中的「原生窗口」是 Dock 进程创建的独立 Tauri/WebView2 顶层窗口，拥有独立 HWND；窗口里的业务界面来自插件 HTML/CSS/JS。它不占主岛 DOM 或设置面板空间。

## 4. 插件声明与公开接口

### 4.1 声明与身份

新增清单能力 `windows` 与 `file-drop`，分别控制窗口管理和文件路径接收。两种能力均独立于 `storage`。窗口页面引用插件已经登记的 `pages[].id`，资源仍必须位于本插件清单并通过摘要检查。

窗口所有者由当前已认证页面票据或后端会话推导，接口不接受插件自行指定 owner/pluginId。记录必须包含插件 ID、包摘要和本次实例代次。旧代次不能创建或控制新实例的窗口。

### 4.2 SDK

浏览器 SDK 新增 `FishDock.windows`、`FishDock.fileDrop`；Node SDK 在 activate/context 中提供同等能力。后端与页面最终走同一个宿主权限及代次检查。支持原生后端使用同一协议方法。

| SDK 操作 | 宿主协议 | 语义 |
| --- | --- | --- |
| `windows.open(options)` | 页面 `dock.windows.open`；后端 `host.windows.open` | 创建本插件外部窗口，页面就绪后返回 opaque handle；同一 key 重复调用复用实例 |
| `windows.update(handle, options)` | 对应 `*.windows.update` | 调整自身窗口尺寸、锚点及位置；不能改资源所有者 |
| `windows.close(handle)` | 对应 `*.windows.close` | 销毁窗口、释放页面票据、事件监听及拖入区域；重复关闭幂等 |
| `windows.onEvent(listener)` | 受控事件桥 | 接收本插件窗口的 ready/closed/anchorChanged/fileDrop 事件 |
| `fileDrop.subscribe(options)` | 对应 `*.fileDrop.subscribe` | 显式申请主 Dock 拖入或自身窗口拖入；返回订阅句柄 |
| `fileDrop.unsubscribe(handle)` | 对应 `*.fileDrop.unsubscribe` | 解除订阅；无消费者后退出拖放命中与捕获状态 |

窗口 options 选择：`key`、`page`、`title`、`width`、`height`、`anchor`、`offsetX`、`offsetY`、`transparent`。anchor 仅支持 `dock-left`、`dock-bottom`、`screen`。screen 允许传屏幕位置，宿主限制在可见工作区。尺寸使用逻辑像素；有限数、尺寸范围及数量在入口校验。每插件最多 4 个、全局最多 16 个窗口。

窗口默认有原生标题栏与关闭入口；透明浮窗模式允许插件自行绘制形状、按钮与动画，并始终保留宿主 Escape 关闭以及托盘「关闭插件窗口」出口。关闭后不会自动重建小球。插件再次显式调用 open 才可重开。

关闭事件包含 handle 与 reason（用户关闭、插件关闭、停用、换版、崩溃或宿主退出）。创建中的请求取消或窗口构建失败也会释放预留名额与票据，不留空白窗口。

## 5. 窗口承载、显示与生命周期

宿主新增最小窗口容器，仅承担插件资源隔离与消息桥；不包含文件暂存 UI，不使用文件管理插件 ID。容器的 iframe 加载本插件已授权资源，主岛与容器可复用页面桥校验逻辑，不赋予插件 Tauri 管理命令权限。

页面票据绑定窗口承载标签，其他窗口不能借票加载该页面。资源协议按已登记承载关系放行，不通过放宽为任意 window label 来实现。禁止插件导航为任意网页或 file URL；远端服务页保持既有受控 gateway 规则，本轮不扩权。

独立窗口在页面 ready 之前隐藏。锚点位置随主 Dock、显示器、DPI 与工作区变化更新，不通过扩大主岛来容纳。默认不占任务栏，显示不抢走当前主界面焦点；用户点击输入时可正常获焦，需处理现有 show_window 的设置页焦点抢回规则。

Dock 全局隐藏、主岛全屏避让时，附着于 Dock 的插件窗口随之隐藏并释放拖放命中；恢复时只恢复原本仍存在的窗口。用户关闭的窗口不恢复。screen 窗口随 Dock 全局隐藏，但不跟随主岛的普通展开/收起。

插件停用、卸载、升级、退出、进程崩溃、账号/存储上下文切换及宿主退出都撤销本实例窗口和订阅。关闭立即释放 WebView；不保留隐藏 renderer。异步创建完成时再次检查所有者代次，防止停用后迟到窗口重新出现。

## 6. 文件拖入与数据隔离

保留经验证有效的 Win32 拖入承载方式，但改为通用接收器。宿主不识别 `stash.*`，只对有 `file-drop` 能力且有效订阅的插件交付路径及目标句柄。

- 拖入主 Dock：插件显式订阅，收到事件后自行决定是否 open 独立窗口。没有订阅时不启用 PR 引入的拖入捕获逻辑。
- 拖入外部窗口：只路由给这个窗口的所有者。窗口关闭或隐藏后移除对应命中区域。
- 主 Dock 订阅为独占；已被另一个活动插件占用时明确返回冲突，不广播文件路径，也不静默改绑。外部窗口各自接收自身区域的拖入。
- 路径只送目标插件当前代次；不能经过全插件广播。进入/离开事件不含路径；真实 drop 才交付路径。日志只记录数量和目标，不打印完整文件路径。
- 拖入在途发生关闭、停用或换版时，事件丢弃并回收落点状态；不对其他插件补发。

## 7. 移除宿主硬编码子岛

移除 `stashSub`、专属 CSS、`StashPanel` 命中区/扩窗接入以及固定文件管理插件调用。保留主岛自身的布局与拖放桥所需通用能力；核对主岛拖放检测尺寸，不再通过默认 500×36 的虚构矩形捕获无订阅区域。

未适配新 SDK 的旧文件管理插件可以继续在设置面板里运行，但不会自动获得外部窗口。SDK 文档提供最小示例：订阅主 Dock 拖入 → 收到路径 → 更新自身业务状态 → open 外部页面 → 用户 close → 宿主释放。示例使用通用插件身份，不把具体插件重新写回宿主。

## 8. Setup 单包更新迁移

### 8.1 2.2.0 的发行资产

GitHub 与 Gitee 均提供 `FISH-Dock-Setup-2.2.0.exe`、`FISH-Dock-Update-2.2.0.exe` 及各自 `.sha256`。GitHub 继续附汇总摘要。Update 以既有 2.1.0 安装归属清单为基线，支持 2.1.0 至 2.1.9 直接升级。

2.2.0 Update 移除下载 Setup 的安装失败兜底，保留安装事务回滚及明确错误。其价值仅为让现有只认 Update 摘要的旧宿主完成过渡；基础资源损坏的旧安装使用完整 Setup 修复。2.2.0 Setup 不含任何 Update 专属兜底脚本。

### 8.2 2.2.0 宿主与后续发行

`updates.rs` 的 GitHub 摘要来源、Gitee 探针和实际下载对象统一选择 Setup。2.2.0 即使看到同一发行中还有 Update，也不选择它。不保留 Update → Setup 的资产回退分支；下载同一 Setup 的 GitHub/Gitee 及既有镜像失败切换保留。

安装版应用内更新仍是下载 → 校验 SHA-256 → 执行 Setup /S → 退出交接。沿用旧安装路径与用户数据；不打开浏览器代替应用内更新。Setup 的完整资源覆盖和安装归属清理继续工作。安装失败必须回滚；不得将 install-update.cjs 因文件名含 update 而误删，它是双包共用的事务安装引擎。

Setup 自带系统 Evergreen 前置检测继续保留。静默安装遇到缺失依赖会失败退出，不能显示更新成功。用户资料、插件和运行时用户数据均不作为受管安装资源删除。

2.2.0 之后的构建/发布入口默认只生成 Setup 和摘要；精简包构建只保留本次过渡所需入口，不再作为常规发行步骤。同步 README、SDK、发行说明和本机工作区约定。

### 8.3 跨版本边界

旧版通过本次双包可以进入 2.2.0，之后只走 Setup。未经过 2.2.0 的旧宿主，尤其只认 Update 摘要的旧版 Gitee 通道，在将来仅 Setup 的 Latest 上可能无法发现更新。后续不伪造 Update 文件名；发行文档明确提供手动 Setup 升级路径，历史 2.2.0 双包保持可下载。

## 9. 验收条件

1. 没有插件申请窗口时，无常驻子岛、小球、隐藏插件 WebView 或新增拖入拦截；主岛点击与收起正常。
2. 合成插件能从后端和设置页分别创建独立 HWND 窗口；业务页面与内部设置页相互独立；重复 key 不产生第二个实例。
3. 关闭按钮、Escape、托盘关闭能真正销毁窗口；再次显示 Dock 不复活已关闭窗口。
4. 停用、卸载、升级、进程崩溃和创建/关闭竞态均撤销窗口、票据、事件及拖入区域；迟到请求不重新建窗。
5. 无能力、伪造 owner、跨插件句柄、过期票据、错误承载窗口、越界资源及未授权页面均拒绝。文件路径不广播，不进入日志。
6. 拖入主 Dock 可让订阅插件按需开窗；拖入插件窗口只发给所有者；无订阅不捕获；主 Dock 独占冲突有可识别错误。
7. 多显示器与不同 DPI 下锚点、隐藏、焦点和输入工作正常；不残留不可关闭或挡点击的空白窗。
8. 2.2.0 更新检查只认 Setup 摘要；GitHub/Gitee 同文件摘要比较一致；仅 Setup 的下一版夹具可正常检查、下载、校验与启动，含 Update 的夹具也不选 Update。
9. 2.2.0 双包解包后版本、归属清单、资源摘要一致；Update 不含下载 Setup 的兜底；Setup 不含固定版 WebView2；安装失败回滚与用户资料保留仍通过。
10. 旧版 → 2.2.0 与 2.2.0 → 仅 Setup 下一版分别验证。无法运行的真实系统测试明确记录阻碍，不用静态检查冒充实机成功。

## 10. 交付与提交边界

按窗口 Hook、拖入路由/移除硬编码、Setup 更新策略、发行资料拆成可单独回滚的原子提交。具体实施排期与验证命令在规格批准后的实现计划中从实际脚本推导。

最终版本为 2.2.0。同步中英文 README、版本渲染图、发行说明与 SDK 使用文档。GitHub/Gitee 正式发行均在实现、检查和包内核验完成后执行；Gitee 保持自有历史，核对树一致，不强推历史。真实现装覆盖测试只在授权的隔离验收环境执行。
