# 性能测试规范

她是常驻程序，用户一天 24 小时开着。性能问题几乎都出在**没人用的时候还在花电**：一直播放的动画、轮询太勤、没变也重画。所以这份规范以「空闲开销」为主，启动时间和内存为辅。

## 1. 什么时候测

改动先在 `dev` 上攒着，发版时才进 main，所以**完整测试只在发版前做一次**，覆盖这期间的所有改动。开发中不做例行测试，只留两道便宜的关：

| 档 | 什么时候 | 做什么 | 大约耗时 |
|---|---|---|---|
| 自动检查 | 每次跑测试（L0）和截图对比（L1） | 截图对比的安静场景里，检查有没有一直在播放的动画（第 2 节最后一行）；有就不通过 | 不额外花时间 |
| 快速对比 | 只在三种情况：改动本身为了性能（要确认确实省了）；新加了一直在跑的东西（新循环、动画、进程、线程）；有人觉得变卡了 | 只测和改动相关的场景，A、B 各跑 1 次（第 4 节，不交替） | 每个场景约 10 分钟 |
| 完整测试 | **发版前** | 全部场景，新版对上一个正式版，按第 4 节交替各 3 次 | 约 3 小时，机器自己跑 |

发版前完整测试不通过时，在 `dev` 这期间的合并点上逐个做快速对比，找出是哪次改动（每个点约 10 分钟）。

只改了设置页、文字、一次性的操作、修 bug（没加常驻的东西）时，什么都不用测。

## 2. 测什么

每次测的都是**整棵进程树**：`wakuwaku.exe`，加上它启动的 WebView2 进程（浏览器、渲染、GPU），以及插件脚本的子进程。

| 指标 | 怎么取 | 说明 |
|---|---|---|
| CPU 周期（主指标） | 每个进程 `QueryProcessCycleTime` 的差，换算成每秒百万周期（Mcyc/s） | 负载很低时，按周期算比按时间算准 |
| CPU 时间 | 每个进程 `TotalProcessorTime` 的差，单位 ms/s；同时换算成「占一个核的百分比」 | 和任务管理器对得上，方便人读 |
| 唤醒次数 | 各线程上下文切换次数之差（性能计数器 `Thread\Context Switches/sec`），每秒几次 | 唤醒多了，就算 CPU 不高也费电（CPU 进不了深睡） |
| 内存 | 进程树的工作集、私有字节 | 取测量窗口结束时的值 |
| GPU | 进程树的 GPU 引擎占用、专用显存（`GPU Engine`、`GPU Process Memory` 计数器） | 动画类的改动主要看这项 |
| 按线程拆分（排查时用） | 线程 CPU 时间之差，加 `GetThreadDescription` 线程名 | Chromium 的线程有名字（CrRendererMain、Compositor、CrGpuMain）；Rust 的线程靠 `spawn_named` 起的名字 |
| 一直播放的动画（检查项） | 用 `/debug/eval` 在各页面跑 `document.getAnimations()`，数无限循环、且正在播放的 | 安静状态下必须是 0；例外写在场景里（比如流光停留期间） |

## 3. 场景

每个场景都有一份固定的设置（`tools/perf/configs/<场景>.json`），由测试副本启动前写入它自己的数据目录，A、B 两边完全一样。

| 编号 | 场景 | 设置和状态 | 安静 |
|---|---|---|---|
| S1 | 岛·静置 | 岛模式，没有会话，没有小工具，插件全关 | 是（90 秒没输入以后才开始测） |
| S2 | 任务栏·静置 | 任务栏模式，默认布局，带监控部件（每 2 秒读一次），一个天气插件 | 是 |
| S3 | 任务栏·有人在 | 同 S2，测量期间每 10 秒在虚拟机里挪一下鼠标（不点击），保持「有人在」 | 否 |
| S4 | 桌面小工具 | 任务栏模式，两块屏各放 2 个小工具、1 块工作台；桌面看得见 | 是 |
| S5 | 会话干活中 | 岛模式，一个会话处于「干活」，计时每秒走（由测试脚本往 `/hook` 发事件模拟） | 否 |
| S6 | 流光停留 | 岛模式，「她有事告诉你时」选流光，停留选「看到为止」；发一次「做完」，在光环转着的时候测 | 否 |
| S7 | 启动 | 冷启动（新的 exe、新的 WebView2 目录）和热启动各 5 次；从 `recent.log` 取「进程启动 → up → 页面就绪 → 任务栏接管完成」各段 | — |
| S8 | 插件全开 | 任务栏模式，她替你跑的插件全部放在任务栏或胶囊里，各自用默认设置 | 是 |

**新功能带来新的常驻状态时，就加一个场景**，比如以后的审批面板、多屏任务栏。

## 4. 怎么测

1. **机器**：一台干净的 Windows 11 测试机（虚拟机即可），不登录任何 agent 账号。测量期间，这台机器上不跑别的测试，宿主机上也不编译、不跑别的虚拟机测试。
2. **A 和 B**：A 是对照（上一个正式版，或者分支的起点），B 是候选。两边都用 release 版 exe，各自单独的数据目录（`WAKUWAKU_USER_DATA`）、端口（`WAKUWAKU_PORT`）和 WebView2 目录，绝不碰正在用的那份。
3. **准备**：启动 → 等 `/health` 报页面就绪 → 预热 60 秒；要求安静的场景，再等到日志里出现 quiet，或者保证 120 秒没有输入。
4. **测量**：每次 60 秒。完整测试：A、B 交替各测 3 次（A B A B A B），抵消机器本身的漂移，每项取中位数。快速对比：A、B 各 1 次，只用来看差别明显的改动；差别在第 5 节的界线附近时，改做完整测试。
5. **记录**：每次的原始数字写成 JSON（版本、提交、场景、机器、每次的读数），汇总成一张 A/B 对比表。
6. **测完**：正常退出两个副本（`/quit`，不要强杀，任务栏模式要靠正常退出才把位置还回去），删掉测试数据目录。

## 5. 怎样算通过

按中位数比，B 和 A：

| 指标 | 通过的条件 |
|---|---|
| CPU 周期、CPU 时间 | 不超过 A 的 110%；如果 A 本身很小，只要多出不到 0.5 ms/s 也算通过 |
| 唤醒次数 | 不超过 A 的 120% |
| 私有内存 | 多出不到 30 MB |
| GPU | 安静场景下不超过 A 的 110% |
| 一直播放的动画 | 安静场景下为 0（场景里写明的例外除外） |
| 启动（S7） | 「进程启动 → 页面就绪」热启动多出不到 100 ms，冷启动多出不到 300 ms |

不通过就先按线程拆开找原因。确实是功能本身就要花的（比如流光停留期间的动画），在提交说明和 issue 里写明数字和理由，由用户决定接不接受。

## 6. 已知的坑

- **刷新率**：动画的开销跟屏幕刷新率成正比。虚拟机是 60Hz，用户的屏幕可能是 144Hz 甚至 280Hz，所以动画类改动在虚拟机里测出来的数，要按刷新率比例往上估；要紧的改动，再在高刷新率的真机上用测试副本复测一次。虚拟机没有显卡，动画的数也偏高，以真机为准。
- **长时间不停的动画**：开销按帧算，和画的是什么几乎无关。实测（2026-10-18，280Hz 屏，RTX 4080 笔记本）：她的窗口每出一帧，Chromium 要约 1 ms CPU，dwm.exe 合成一帧还要约 0.8 ms。满帧不停地动，哪怕只是一个 10 px 的小方块，也是半个核的量级；去掉发光、缩小范围、换窗口样式都不省。所以动画要么做短（几秒内结束），要么交给系统合成器（DirectComposition / Windows.UI.Composition，她的进程每帧不干活）并限帧（60 帧约为满帧的五分之一）。安静、全屏、勿扰、隐藏时一律停住。
- **自己别吵着它**：别在被测的那台机器上同时跑 agent。每个钩子事件都会让岛重画一次，数就不准了。
- **WebView2 共用进程**：两个副本如果用同一个 WebView2 目录，会共用浏览器和 GPU 进程，数会混在一起。所以每个副本必须用自己的 WebView2 目录。
- **任务栏闪烁的按钮**：别的程序在任务栏上闪烁时，按钮动画也算在她头上（以前测到过一个核的 40%）。测量前确认没有窗口在闪。
- **第一次启动**：新 exe 第一次启动时，杀毒软件可能先扫一遍，冷启动要多测几次取中位数。

## 7. 工具（`tools/perf/`，待写）

| 脚本 | 做什么 |
|---|---|
| `run.ps1 -A <exe> -B <exe> -Scenes S1,S2 -Runs 3` | 在测试机上按第 4 节的步骤跑完，产出 JSON 和对比表 |
| `measure.ps1 -Root <pid> -Seconds 60` | 测一棵进程树：周期、时间、唤醒、内存、GPU；加 `-Threads` 按线程拆分 |
| `animations.ps1 -Port <n>` | 用 `/debug/eval` 列出各页面正在播放的无限动画 |
| `report.js <a.json> <b.json>` | 出对比表，标出不通过的项 |
| `configs/*.json` | 各场景的设置 |

脚本只依赖 Windows 自带的 PowerShell 和 Node，在测试机上运行。

## 8. 基线

每个正式版、每个场景记一行中位数（CPU 周期、ms/s、唤醒、私有内存、GPU、启动时间），加上测试机和日期；新版发布前对上一行比。测试机要固定，配置也不变（分辨率、缩放、显示器数量），不同版本的数字才能比。具体的机器和数字跟着测试机走，不放在仓库里。
