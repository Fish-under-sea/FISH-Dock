# Fish Dock 内置 OFM、邮件与窗口行为改进方案

日期：2026-10-22（Asia/Shanghai）

状态：用户已批准，当前处于实现与验收阶段，后续明确由主代理直接执行，不使用团队委派。本文保留初始设计依据，最新实现、测试和剩余项见 [工作总结](../../../../Fish-Dock-OFM-工作总结-2026-10-22.md)。当前安装版没有被替换，尚未发布安装包。

## 1. 目标与范围

本次拆成五项独立需求：

1. 定位并修复 Fish Dock 内置 OFM 的 WorkBuddy 兼容问题，参考当前上游 issue 和 PR。
2. 邮件增加一键已读，作用于当前选择的邮箱；选择聚合邮箱时支持所有已绑定邮箱。
3. 进入 OFM 标签页时默认锁定并置顶，主动关闭面板或切换其他 Fish Dock 标签页时关闭两项状态；当前次进入中手动取消后保持用户选择。
4. OFM 增加 Meoo 渠道，复用现有账号管理体验，目标是浏览器登录绑定后即可调用模型，而不是让用户手动粘贴 Cookie。
5. 核实商汤小浣熊每日 300 积分的触发机制，验证一键领取或一键登录触发发放的可行性。

明确排除：整体覆盖升级 OFM、重写邮件客户端、改动其他渠道提示词、自动付费、自动创建云项目、将一次性奖励冒充每日签到、直接修改用户数据目录或账号库。

路径约定：下文 `Wakuwaku/` 和 `dsh-our-free-model/` 均相对于本方案所在项目的父级产品目录。它们是两个独立工作树，验收和改动清单分别记录。

### 3.2 本地定位

- `dsh-our-free-model/package.json` 当前标记为 2.5.3，但工作树有多项既有修改；版本号本身不足以判断修复是否存在。
- `vendor/channel-pack/src/openai-gateway/tencent-fingerprint.ts` 当前规则表只包含 Git 上下文模板句，注释和入口限定 system；尚未覆盖上述 assistant 历史增量。
- `vendor/channel-pack/src/buddy-adapter.ts` 已有 `11128` 排除账号策略拦截的判断，实施时先补回归保护，不重复添加相同修复。
- `Wakuwaku/src-tauri/src/oflm.rs` 拉起 OFM standalone 服务；开发与安装资源路径不同。修复必须进入实际服务资源，而非只更新插件用的 bundle。
- `Wakuwaku/scripts/stage-ofm.mjs` 负责拷贝独立渠道与网页产物；当前脚本会清空目标目录，实施前需检查目标绝对路径，并采用隔离输出先验收。

### 3.3 推荐路径

采用「保留本地版本和现有渠道，按证据定向移植」；不整包升级，不直接套入整份 PR。

1. 用脱敏诊断确认错误属于登录、模型目录、请求序列化、流解析还是资源版本。记录渠道、模型、错误码、请求角色与加载目录，不记录 token 或消息正文。
2. 建立最小对照：干净提示词、身份句在首条/后续 system、在 assistant 历史、在 user/tool 中、带工具调用的多轮会话。
3. 若本机复现与上游一致，在两条腾讯渠道共用的出站层统一处理经过确认的模板文本，覆盖 Chat、Responses 及直接适配器路径，避免只修某个 UI 入口。
4. 改写范围仅限经过证据确认的 system/assistant 文本；用户消息、工具结果、工具参数 JSON、图片块和其他渠道原样保留。普通文本逐字符保持不变，避免扩大缓存失效。
5. 保留 11128、401、429、内容审核和网络错误的独立分类。11128 不触发账号池轮换冷却，也不进行无上限自动重试。
6. 对 SSE 中返回的业务错误与 HTTP 错误采用一致分类；保留原始错误码供诊断。
7. 更新源码后按仓库构建链生成 standalone 渠道与网页产物；隔离 stage 后核对文件清单和哈希，再验证 Fish Dock 实际载入的那一份。

### 3.4 验收

- 同一账号与模型的干净对照、受影响历史、多轮工具调用均有可复现结果。
- user/tool 内容与非腾讯渠道请求保持不变。
- 11128 不导致账号池批量进入冷却；401/429 等既有行为保留。
- 源码、生成渠道、开发资源、安装资源的来源与版本可追踪。
- 真实调用仍失败时交付具体响应和分层定位，不以单元测试代替线上可用性结论。

## 4. 邮件一键已读设计

### 4.1 交互范围

在邮件工具栏增加「全部已读」图标按钮，使用现有图标体系并提供 tooltip 与无障碍名称。

- 选择单邮箱：处理该邮箱收件箱的未读邮件。
- 选择聚合邮箱：处理所有已绑定邮箱收件箱的未读邮件。
- 搜索、星标或列表分页不改变该操作的邮箱范围；操作反馈明确邮箱范围和数量。
- 空未读状态禁用；处理中禁用重复点击；聚合操作显示逐邮箱成功与失败，不以一个失败中止其他邮箱。

### 4.2 后端语义

已有能力位于 `Wakuwaku/src-tauri/src/mail/letters.rs`、`mail/imap.rs` 和 `mail/store.rs`；`src/pet/bridge.js` 负责前端调用桥接。

建议新增专用批量命令，而非逐封调用打开正文：

1. 在服务器选定收件箱，校验 UIDVALIDITY，查询当前未读 UID，固定本次操作集合。
2. 仅对固定 UID 集合分块执行 `UID STORE +FLAGS.SILENT (\\Seen)`；使用稳定 UID，不使用会随新邮件变化的消息序号。
3. 每个邮箱复用同一次连接，按请求长度分块。操作期间新到邮件不纳入本次已读集合。
4. 服务端确认后更新本地缓存并持久化，递增邮件 revision，刷新列表与未读徽标。后台同步不得用旧快照覆盖刚确认的已读状态。
5. 返回成功数量、失败数量和逐邮箱错误。部分成功只提交已确认集合；超时等不确定结果通过重新查询核实。
6. 不把未被修改的邮件一律反转标记作为回滚，避免幂等调用把原本已读的邮件改成未读。

### 4.3 变更与验收

主要范围：`Wakuwaku/src/pet/settings.js`、`bridge.js`、Rust 邮件模块、命令注册及现有多语言资源。

测试覆盖空集合、多邮箱、超过前端 50 封分页、较大 UID 集合、UIDVALIDITY 变化、断线、部分成功、同步并发和操作中新邮件。验收以服务器标记、本地列表、收件箱数量和 Dock 未读徽标一致为准。

## 5. OFM 锁定与置顶设计

### 5.1 明确行为

| 事件 | 锁定 | OFM 设置页置顶 |
| --- | --- | --- |
| 从其他标签进入 OFM | 开启 | 开启 |
| 直接打开 OFM，或关闭后再次打开且仍停在 OFM | 开启 | 开启 |
| 数据刷新、iframe 加载完成或模型列表更新 | 保持当前选择 | 保持当前选择 |
| 当前次进入中手动关闭置顶 | 保持锁定 | 关闭 |
| 当前次进入中手动关闭锁定 | 关闭 | 关闭 |
| 切换 Fish Dock 的其他顶级标签页 | 关闭 | 关闭 |
| 点击关闭或按既有关闭快捷操作关闭面板 | 关闭 | 关闭 |
| 切换 OFM iframe 内的账号、设置等内部页签 | 保持当前选择 | 保持当前选择 |
| 为登录切换到外部浏览器 | 默认保持 | 默认保持 |

「别的标签页」按 Fish Dock 顶级标签解释，不把外部浏览器标签或 OFM 内部子页面误判为离开 OFM。

### 5.2 实现原则

- 入口位于 `Wakuwaku/src/pet/settings.js` 的 `open`、`setTab`、`close`，原生联动位于 `src-tauri/src/island.rs::keep_on_top`。
- 以统一的进入/离开控制器管理生命周期，不在 `draw`、iframe 重绘或网络响应里重复开启。
- 自动开启属于当前面板会话态，与用户永久偏好分开。现有锁定/置顶按钮显示有效状态，并可随时手动取消。
- 退出 OFM 时按用户要求将两项有效状态关闭，不恢复进入前的 true 状态；仅取消本次 OFM 管理的设置页状态。
- 异步更新串行或带会话代次，快速切页与关闭后迟到响应不得重新开启。
- 原生窗口采用现有状态模型；保持 Dock 收起时原有的桌面停靠行为，避免把设置页置顶和整个 Dock 的常驻层级混为一谈。

### 5.3 验收

自动化验证状态转换、重复进入、手动取消后刷新、快速切页和迟到响应；Windows 实机验证真正的 always-on-top、失焦不关闭、登录浏览器可操作、关闭后状态清理。浏览器截图不代替原生置顶验证。

## 6. Meoo 渠道设计与协议关卡

### 6.1 已有公开依据

- [官方 CLI 文档](https://docs.meoo.com/meoo-cli)：`meoo login` 自动打开浏览器，由用户确认设备并授权，CLI 保存登录凭证。
- [官方云服务模式](https://meoo.com/skill/references/cloud-patterns.md)：模型接口为 `https://api.meoo.host/meoo-ai/compatible-mode/v1/chat/completions`，示例使用项目级 `MEOO_PROJECT_API_KEY`，不是直接使用网页登录 Cookie。
- 文档示例列出 `qwen3.6-plus`、`kimi-k2.5`、`deepseek-v3.2`、`glm-5`、`MiniMax-M2.5`。这是文档列表，实际可用性及费用以账号返回为准。

结论：有登录与模型服务基础，但「登录授权成功」和「取得可调用模型的凭证」尚未连成经本机验证的完整链路。

### 6.2 先验证再承诺

阶段 A 只回答四个问题：

1. 官方登录授权的发起、回调或轮询、凭证有效期和刷新协议是什么？
2. 账号凭证能否直接调用模型；若依赖项目，现有项目如何列举、选择并获得模型服务权限？
3. 项目模型额度与账号网页额度是否同一池，是否需要付费或额外开通？
4. 模型是否支持 SSE、多轮会话、tools/tool_choice、取消与正确 usage 返回？

默认只使用用户主动绑定的账号和现有项目；不静默创建云项目、开通计费服务或读其他应用的凭证库。需要网站确认时明确显示登录或项目选择状态，而非假装已经连通。

### 6.3 验证通过后的接入

新增 Meoo 产品配置、认证、适配器与渠道注册，接入 OFM 既有账号列表和凭证存储。管理界面提供「Meoo → 添加账号 → 浏览器登录 → 绑定完成」，支持取消、超时、刷新和删除。

- 模型列表优先用服务端可发现目录；没有目录接口时只列真实验证通过的配置，不照抄宣传列表。
- 登录凭证与项目级模型密钥分类型保存，不出现在前端状态、URL、日志或诊断导出中。
- 若必须选择现有项目，首次绑定时提供项目选择；后续自动使用已绑定项目。
- 凭证刷新采用单飞，401 至多刷新重试一次；429/额度耗尽按既有渠道策略处理。
- 支持本地 OpenAI 网关与账号池；仅当实测支持时声明工具、视觉、思考等能力。

### 6.4 验收门槛

新登录、已有登录刷新、重启恢复、删除账号、两个账号隔离；本地网关模型发现；非流式与流式聊天；真实工具调用闭环；401、429、取消、额度耗尽与 SSE 分片。只有整条链路通过才标记为「登录绑定后可用」。

若官方权限要求超出上述默认范围，先交付协议结论和所需用户步骤，Meoo 任务保留未完成，不用空渠道卡片结案。

## 7. 商汤每日积分的一键触发设计

### 7.1 三种积分来源必须分开

本地 `dsh-our-free-model/vendor/channel-pack/src/raccoon-credits.ts` 已区分：

| 来源 | 历史实现记录 | 本次处理 |
| --- | --- | --- |
| 注册奖励 | 注册时自动发放 | 不当成签到 |
| 桌面端登录奖励 | `POST .../login/points/grant`，默认 3000，重复为 `granted:false` | 保留一次性任务语义 |
| 每日积分 | 旧记录认为服务端 daily_grant 自动发放 | 对照当前版本重新验证触发与有效期 |

公开的 [商汤小浣熊版本说明](https://m.weibo.cn/status/5346017396392783) 提到：当天登录后，当日发放每日积分有效期延长至 7 天；免费版每天 300，升级版本每天 500。该公开说明与本地旧注释的时间和语义有差别，应以当前账号实测为准。

### 7.2 验证流程

1. 用户主动登录绑定后，读取积分余额、积分包与账单，保留脱敏基线。
2. 在官方当前版本执行一次正常登录或领取动作，观察真实网络调用与对应账单。
3. 分辨它属于独立领取请求、登录触发发放、已有自动发放后的有效期更新，还是只刷新余额。
4. 再次点击验证幂等；确认免费/会员额度由服务器返回，不写死所有账号均为 300。
5. 验证跨日行为与服务端业务时区；仅同一天测试时，报告里明确跨日尚未验收。

### 7.3 按实测落地

- 有独立领取接口：接入现有签到能力，按钮返回领取结果并刷新余额与账单。
- 登录请求触发发放：实现一键登录触发与结果核验，界面名称保持真实，不声称调用不存在的签到接口。
- 自动发放：展示今日发放状态与刷新入口，不制造虚假的「领取成功 +300」。
- 只有一次性 3000：仍归新手奖励，不登记为 dailyCheckin。

点击状态至少区分已发放、本次新增、需重新登录、请求失败和发放待确认。以账单业务事件和服务器领取结果确认新增，余额变化只作辅助，避免并发模型消费造成误判。默认不增加后台定时自动领取，也不在打开面板时静默调用领取请求。

## 8. 依赖顺序与协作边界

设计审阅通过后再建立最小任务图，不启动未批准的实现。

1. 共同基线：记录两个工作树的既有改动，确认当前实际运行的资源来源，补特征测试。
2. 并行 A：渠道负责人先修 WorkBuddy；随后验证 Meoo 与商汤协议。渠道文件由同一负责人串行处理，避免多人改注册表冲突。
3. 并行 B：Dock 负责人先实现邮件已读，再实现窗口生命周期。共享 `settings.js` 的两项改动由同一负责人完成。
4. 独立验收：QA 对照规格与实际 diff，先规格合规，再代码质量；检查真实请求与原生窗口证据。
5. 集成：重建 standalone 与 Dock 资源，在隔离输出验证后交付可追踪的产物。发布或替换当前安装版另行确认。

推荐三名成员：渠道、Dock、独立 QA。Meoo 或商汤的协议阻塞不阻止已验证的邮件与窗口改动验收，也不抹去尚未完成的渠道目标。
